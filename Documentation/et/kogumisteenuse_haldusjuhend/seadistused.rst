..  IVXV collector service administration guide

Collector Service Settings
==========================

Logging Settings
----------------

Collector service logs are kept at the location where they are generated and
duplicated to log servers. By default, the *syslog* service ``rsyslog`` is used
for collecting and forwarding logs.

The collector service supports two types of log servers, which are
described in the collector service technical settings.

#. The collector service log collection service is an internal service of the
   collector service and there may be multiple instances of it in the system.

#. The activity monitoring server is an external service for the collector
   service and there can be only one instance of it.

When applying technical settings to the collector service, the management service
installs the log collection service before other services, so that logs produced
by services can be collected by the log collection service as early as possible.

.. note::

   Collector service log messages are generated after the election settings are
   loaded for the first time, since services are started after loading these
   settings.

Log Configuration of a Log-Producing Service
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The logging configuration for a log-producing service is generated by the
management service according to the technical settings.

#. Each service logs to the local *syslog* service;

#. The *syslog* services on all service machines are configured to save
   collector service logs to the local file system (:file:`/var/log/ivxv/ivxv-YYYY-MM-DD-HH.log`);

#. The *syslog* services on all service machines (except the log collection
   service) are configured to forward over the network:

   #. All log entries to the log collection service (protocol: RELP);

   #. Collector service log entries to the activity log monitoring server
      (protocol: RELP);


Log Collection Service Configuration
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The log collection service configuration file comes from the service software
package (:ref:`ivxv-logcollector.conf <ivxv-logcollector.conf>`).

#. The log collection service accepts log entries via the RELP protocol;

#. Collector service log entries are written in JSON format to the file
   :file:`/var/log/ivxv/ivxv-YYYY-MM-DD-HH.log` (excluding request and
   debug logs);

#. Collector service request logs are written in rsyslog standard format to the
   file :file:`/var/log/ivxv/ivxv-request-YYYY-MM-DD-HH.log`;

#. Collector service debug logs and logs of other important services (haproxy,
   etcd, rsyslog, sshd) are written in rsyslog standard format to the file
   :file:`/var/log/ivxv/ivxv-debug-YYYY-MM-DD-HH.log`.


Storage Service Settings
------------------------

Currently, the only storage service implementation uses the distributed
key-value database ``etcd``. Multiple ``etcd`` instances are run simultaneously,
which achieve consensus among themselves regarding stored data.

For smooth operation of the storage service, it may be necessary to tune some
``etcd`` parameters for the specific deployment environment. To do this, create
a file :file:`/etc/default/ivxv` on the service machine and add the lines
described in the following sections. After creating the file or modifying its
contents, the storage service must be restarted to apply the new values. If a
parameter is not specified, the default value is used.

The ``etcd`` documentation at
https://coreos.com/etcd/docs/latest/tuning.html is helpful when selecting
setting values.

Time Parameters
^^^^^^^^^^^^^^^

The ``etcd`` cluster elects one of its members as leader, which coordinates all
data changes. In addition, the leader periodically pings all other cluster
members to help detect situations where the connection to the leader is lost:
if a cluster member has not received a ping for a sufficiently long time, it
initiates a new leader election.

Due to higher network or disk latency, the leader's ping may be delayed too
much, causing a new leader election. During failures, leader changes are a
natural part of the system, but for a working system, they are unnecessary
load. Therefore, the leader's ping frequency ``ETCD_HEARTBEAT_INTERVAL`` and
other members' timeout ``ETCD_ELECTION_TIMEOUT`` should be configured according
to the deployment environment latency::

   ETCD_HEARTBEAT_INTERVAL=100
   ETCD_ELECTION_TIMEOUT=1000

Both values are in milliseconds, with defaults of 100ms and 1000ms respectively.

.. important::

   All storage service instances in one cluster must have the same time
   parameters. Otherwise, stability problems may occur due to different
   ping expectations.


Snapshot Parameters
^^^^^^^^^^^^^^^^^^^

``etcd`` maintains a log of all data changes. To prevent the log from growing
too large, periodic snapshots of the database state are taken and the previous
log is deleted. If the storage service uses too much memory or disk space,
more frequent snapshots may help.

A new snapshot is taken after every ``ETCD_SNAPSHOT_COUNT`` data changes,
so a lower value results in more frequent snapshots and a smaller log size::

   ETCD_SNAPSHOT_COUNT=10000

By default, a snapshot is taken after every 10000 changes.
